# Capítulo III: Requirements Specification
En este capítulo se presentan los requisitos especificados de DoofPlus, acorde al análisis de la problemática, los segmentos objetivo y el alcance obtenido durante el desarrollo. La especificación cubre tres productos de la solución: la landing page pública, la aplicación web frontend y los servicios backend RESTful implementados con una arquitectura basada en bounded contexts.


## 3.1. User Stories

Las User Stories se obtuvieron a partir de las necesidades identificadas en las entrevistas, los User Personas, el User Task Matrix y el Big Picture EventStorming del capítulo II. Se organizan en 11 epics que agrupan 59 User Stories y 11 Technical Stories, presentadas en un único cuadro con una fila por epic o historia:

- **Landing Page (EP01):** historias redactadas con el rol de visitante o de visitante de un segmento (especialista QA/QC o jefe de producción), que cubren las secciones del sitio estático y su vínculo con la Web Application.
- **Web Application (EP02 a EP11):** historias de los roles de especialista QA/QC, jefe o supervisor de producción y administrador del laboratorio, agrupadas por capacidades del negocio: identidad y accesos, documentación de calidad, trazabilidad de lotes, desviaciones y CAPA, integración IoT, cumplimiento y auditoría, dashboards, operaciones de laboratorio, comunicación entre áreas y suscripciones.
- **Technical Stories (TS01 a TS11):** redactadas con el rol Developer. TS01 corresponde a la implementación de la Landing Page y las demás a los endpoints del RESTful API de cada epic, con escenarios de request y response.

Los criterios de aceptación siguen la estructura de Gherkin (Dado que / Cuando / Entonces), se redactan en tiempo presente y en tercera persona, no hacen referencia a detalles de la interfaz de usuario y son comprobables.

## 3.3. Product Backlog

El Product Backlog de DoofPlus consolida las 59 User Stories y las 11 Technical Stories de la sección 3.1, con su estimación en Story Points, y las ordena según el valor que aportan al negocio con los siguientes criterios:

1. **Landing Page primero:** sus historias se ubican al inicio porque el sitio estático es el primer punto de contacto con los laboratorios y, según el statement, se considera desde el primer sprint.
2. **Valor de las historias de la Web Application:** se mide con el User Task Matrix de la sección 2.3.2. Cada tarea recibe un puntaje igual a la suma, para ambos User Personas, de su frecuencia (Often = 3, Occasionally = 2, Rarely = 1) multiplicada por su importancia (High = 3, Medium = 2, Low = 1), y las historias que apoyan cada tarea se ordenan de mayor a menor puntaje. Cada grupo termina con la Technical Story del API que lo soporta.
3. **Dependencias:** cuando una historia exige otra en sus criterios de aceptación, la requerida se ubica antes. Por ejemplo, US14 requiere un producto con fórmula maestra aprobada, por lo que US35, US36 y la orden de producción (US57) la preceden.
4. **Identidad y suscripciones al final:** las historias de autenticación y roles no se colocan al inicio, como indica el statement. Las de suscripción y pago cierran el backlog porque la estrategia comercial de la sección 2.1.2 ofrece una prueba piloto de 30 días, de modo que el cobro se activa cuando el laboratorio ya usa el flujo de calidad.
